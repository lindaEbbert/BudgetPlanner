# 13: Status-Hinweise auch beim automatischen Vorschlag

**What to build:** Der automatische Vorschlag (Verlassen des Namensfelds,
Wahl des Typs) läuft heute für den Nutzer unsichtbar: Solange die Anfrage
läuft, zeigt das Transaktionsformular nichts, und kommt kein Vorschlag, auch
nichts. Ob überhaupt ein Vorschlag geholt wurde, sieht man nur in den
Server-Logs. Der Button aus [Ticket 05](05-manueller-vorschlag-button.md)
zeigt dagegen „Vorschlag wird geholt…“ und „Keine Kategorie vorgeschlagen.“.
Künftig zeigt der automatische Vorschlag dieselben beiden Hinweise.

Das ändert eine Festlegung aus dem Spec („keine sichtbare Störung“) und aus
[Ticket 04](04-auto-vorschlag-leeres-feld.md) („ohne Fehlermeldung“).

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

## Acceptance criteria

- [ ] Solange ein automatisch ausgelöster Vorschlag läuft, erscheint
      „Vorschlag wird geholt…“ im bestehenden Status-Hinweis (`role="status"`)
- [ ] Kommt der automatische Vorschlag leer zurück — auch bei Fehler oder
      Timeout —, erscheint „Keine Kategorie vorgeschlagen.“; der Hinweis
      verschwindet wie beim Button bei der nächsten Formularänderung
- [ ] Eine Meldung für beide Fälle: „Modell fand nichts“ und „Dienst nicht
      erreichbar“ werden nicht unterschieden (die API liefert in beiden
      Fällen dieselbe leere Antwort)
- [ ] Hat der Nutzer während der Anfrage die Category selbst gesetzt oder
      eine Fixkosten-Zuordnung gewählt, erscheint kein „Keine Kategorie
      vorgeschlagen.“ — die Antwort ist dann ohnehin hinfällig
- [ ] Wird eine laufende automatische Anfrage durch eine neuere ersetzt,
      bleibt „Vorschlag wird geholt…“ stehen, bis die neuere antwortet; eine
      verworfene Anfrage setzt den Hinweis nicht zurück
- [ ] Das Verhalten zwischen den Auslösern bleibt wie in Ticket 05: Der
      automatische Vorschlag überholt eine laufende Button-Anfrage nicht, und
      der Button bleibt während einer automatischen Anfrage bedienbar
- [ ] Die Aktionen nach einem Treffer bleiben unverändert: bestehende
      Category → Feld wird belegt; nur `newCategoryName` → Bestätigungs-Hinweis
- [ ] `spec.md` (Abschnitt zu Fehlern beim Suggestion-Aufruf) und das
      Kriterium „ohne Fehlermeldung“ in Ticket 04 verweisen auf dieses Ticket
- [ ] Tests über TestBed mit `HttpTestingController`: Hinweis während der
      Anfrage, leere Antwort, Fehlerantwort, zwischenzeitlich gesetzte
      Category, ersetzte Anfrage

## Hinweise zum Code

- `TransactionFormComponent` (`frontend/src/app/features/transactions/
  transaction-form/`): Der Status hängt heute am Signal
  `requestedSuggestion` (`'none' | 'waiting' | 'nothing'`), das nur
  `suggestCategoryOnRequest()` setzt. `suggestCategoryIfOpen()` prüft
  `requestedSuggestion() === 'waiting'`, um eine Button-Anfrage nicht zu
  überholen — wer gerade wartet, muss also weiterhin unterscheidbar bleiben,
  auch wenn beide Auslöser denselben Hinweis zeigen.
- `requestSuggestion()` verwirft eine laufende Anfrage per `unsubscribe()`;
  der Callback der verworfenen Anfrage läuft dann nicht mehr.

## Out of scope

- Unterschiedliche Meldungen für „nichts gefunden“ und „Dienst nicht
  erreichbar“ — bräuchte eine Änderung am Backend-Vertrag
- Unbekannte `categoryId` im automatischen Vorschlag →
  [Ticket 09](09-unbekannte-category-id-im-vorschlag.md); ist 09 umgesetzt,
  führt so eine ID auch hier zu „Keine Kategorie vorgeschlagen.“
- Umbau der Formularwerte auf Signals →
  [Ticket 10](10-formularwerte-als-signals.md)
