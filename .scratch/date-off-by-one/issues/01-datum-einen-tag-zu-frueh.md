### Verifikation

Nachgestellt in Europe/Berlin (UTC+2):

```
new Date(2026, 8, 30).toISOString().split('T')[0]  →  "2026-09-29"
```

Der Datepicker (`provideNativeDateAdapter`) liefert ein `Date` für lokale
Mitternacht. Beim Speichern wird es mit `toISOString()` in UTC umgerechnet und
am `T` abgeschnitten, also landet in Zeitzonen östlich von UTC der Vortag im
Payload. Das Backend (`transaction_date` bzw. `start_date` als `Date`-Spalte)
speichert, was ankommt; es ist nicht beteiligt.

## Agent Brief

**Category:** bug
**Summary:** Datumsfelder im Frontend werden beim Speichern über UTC
umgerechnet und landen dadurch einen Tag zu früh im Backend.

**Current behavior:**
- Transaktionsformular (Anlegen und Bearbeiten): Das im Datepicker gewählte
  Datum wird als Vortag gesendet. Das vorbelegte „heute“ (`new Date()`) wird
  zwischen 00:00 und 02:00 Uhr Ortszeit ebenfalls als Vortag gesendet.
- Beim Bearbeiten wird das gespeicherte `transactionDate` (`"YYYY-MM-DD"`) mit
  `new Date(string)` eingelesen, also als UTC-Mitternacht. Östlich von UTC
  zeigt der Picker dadurch zufällig das richtige Datum an, westlich von UTC
  den Vortag.
- Fixkostenformular: `startDate` wird auf dieselbe Weise umgerechnet und
  ist ebenfalls einen Tag zu früh.

**Desired behavior:**
Das Datum, das der Nutzer im Picker sieht, ist genau das Datum, das als
`YYYY-MM-DD` ans Backend geht, unabhängig von Zeitzone und Uhrzeit. Beim
Bearbeiten zeigt der Picker genau das gespeicherte Datum. Datumsangaben
werden in beide Richtungen aus lokalen Datumsteilen (Jahr, Monat, Tag)
gebildet, nie über UTC.

**Key interfaces:**
- `CreateTransactionDto.transactionDate` und das `startDate` im DTO für
  Fixkosten: bleiben `string` im Format `YYYY-MM-DD`, keine Typänderung.
- Eine gemeinsame Hilfsfunktion in `shared` (z. B.
  `toIsoDate(date: Date): string` und `fromIsoDate(value: string): Date`),
  die beide Formulare nutzen, statt `toISOString().split('T')[0]` bzw.
  `new Date("YYYY-MM-DD")`.

**Acceptance criteria:**
- [x] Ein im Transaktionsformular gewählter 30.09.2026 wird als
      `"2026-09-30"` gesendet (Anlegen und Bearbeiten)
- [x] Das vorbelegte „heute“ wird auch kurz nach Mitternacht Ortszeit als
      heutiges Datum gesendet
- [x] Beim Bearbeiten einer Transaktion mit `transactionDate: "2026-09-30"`
      zeigt der Picker den 30.09.2026, auch in einer Zeitzone westlich von UTC
- [x] Ein im Fixkostenformular gewählter Starttermin wird unverändert als
      `YYYY-MM-DD` gesendet
- [x] Im Frontend-Code gibt es kein `toISOString().split('T')[0]` mehr, um
      ein Datum ohne Uhrzeit zu bilden
- [x] Tests für die Hilfsfunktion decken eine Zeitzone östlich von UTC
      (z. B. `Europe/Berlin`) und eine westlich von UTC ab, jeweils für
      lokale Mitternacht und eine Uhrzeit kurz nach Mitternacht; `ng test`
      läuft grün

**Out of scope:**
- Backend-Änderungen (der `Date`-Typ dort ist korrekt)
- Bereits falsch gespeicherte Transaktionen oder Fixkosten korrigieren
- Wechsel des Date-Adapters (z. B. auf Luxon oder date-fns)
- Monatsauswahl, Dashboard und Budgets, die `new Date()` nur für Monat und
  Jahr nutzen
